## Calendar MVP

1. Build a mobile-friendly in-app calendar with a readable month view and an upcoming list. Show internship/job application deadlines and personal application reminders from the student's own saved applications using Keyan's authorized, user-scoped adapter when ready; add contact follow-up dates from the approved contacts adapter later. Use clearly fictional fixtures while waiting. Each item links to its application or job, displays the job/company and date type, and lets the student inspect details without relying on hover. Clearly distinguish a **verified posting deadline**, an unverified posting deadline, and the student's **personal reminder/application date**. Unknown dates stay unknown. No student can view another student's events.
2. Show upcoming reminders inside the app (for example, due soon/today/overdue) based on saved dates. Handle local time zones and date-only values consistently. On first delivery, an in-app upcoming list and visible reminder state are enough; do not claim background delivery when the site is closed. Reminders should have useful empty, loading, and error states.
3. Provide an obvious **Add to calendar** action on an event or application detail. For a dated event, offer a Google Calendar prefilled event link and a standards-compliant `.ics` download/share fallback for Apple Calendar, Outlook, and other calendars that can import ICS. On phones, design the normal path to take only a couple of taps where the device/browser supports it; test on actual available mobile browsers and document extra OS import/share steps honestly. The app cannot promise automatic addition or two-tap behavior on every device.
4. Generate all-day ICS events for date-only deadlines/reminders, with a stable unique event id, correct start/end dates, safe escaped text, and no invented time or deadline. Avoid duplicates where feasible. Never include private résumé/profile material or a private application URL in a public calendar export. If the user chose a personal reminder date, label it as such.
5. Connect the calendar to Steve's saved-application UI by handing Steve a small documented prop, link, or export function. Steve adds or approves changes within his routes/nav; do not edit his files yourself. Coordinate with Keyan for existing fields and adapters; request any schema/contract change from Keyan and Dallas instead of adding new tables.

Write focused unit tests before implementing calendar behavior: missing date, all-day boundaries, text escaping, personal-versus-posting date labels, private-data omission, and event ordering. After a runnable calendar exists, use Playwright for phone/desktop calendar navigation, upcoming reminder states, and export actions. Test against fictional fixtures first and label fixture-only results; add ordinary-session persistence/isolation checks when the adapters are ready. Run available typecheck, unit tests, build, and relevant browser checks. Report NOT RUN with reasons.

## Contacts and follow-up after the core calendar works

The intended calendar also helps students maintain professional relationships. After Keyan confirms a private, user-scoped contacts/meetings schema and adapter, build a simple contacts screen and show follow-up dates in the calendar. Record a person's name, organization/role, user-entered contact details, when/how they met, meeting date, and notes about what they discussed; let the student add/edit/delete notes and set or change the next follow-up reminder. Never expose contacts to employers or other students. If Keyan cannot supply this safely before the deadline, keep the working calendar and record contacts as a clearly named follow-up, without pretending fictional contacts are persisted.

Offer **editable suggestions** for when to reach out and what to discuss, based on the student's own last-meeting notes and chosen reminder interval. Show which note or date supports each suggestion, avoid invented personal details, and never send a message automatically. A simple rules-based suggestion is enough for the first version; a later Claude suggestion may use private notes only after clear disclosure and explicit user action. Treat contact information and meeting notes as private data; do not log or export them accidentally. If a contact reminder is exported, include only the user-approved event text.

Write tests first for student A/B isolation via Keyan's ordinary-session adapter, note edits/reload, user-editable reminder dates, calendar display, and suggestions grounded in saved notes. Will owns only the contacts UI/logic/route paths listed above; Keyan owns SQL/RLS/adapters, Dallas owns any new shared contract, and Steve owns navigation integration. Request those handoffs before connecting persistence.
